Let's review the migration of the payment orchestration layer from the monolith to the distributed architecture. The main constraint is that we cannot introduce duplicate charges while we move traffic gradually.

The current design has the checkout service calling the payment gateway adapter synchronously. In the new design, checkout publishes a PaymentRequested event to Kafka, and the orchestration service consumes it.

For ordering, we are using Kafka partitions keyed by payment_id. That gives us ordering for events with the same key, but it does not give global ordering across all payments.

The consumer group will run three replicas initially. We should not assume that three replicas means three active leaders, because Kafka assigns partitions and only one consumer in the group owns a partition at a time.

For the database, the ledger remains on PostgreSQL. We are using serializable transactions only around the balance mutation, not around the entire request lifecycle.

The idempotency table is keyed by merchant_id and idempotency_key. The STT system wrote this as item potency table in one place, but the actual identifier is idempotency_key.

We also have a unique constraint on merchant_id, idempotency_key, and operation_type. If a retry arrives with the same key and a different amount, we reject it instead of silently updating the original request.

For the cache, Redis is only an optimization. We must not treat a Redis hit as proof that a payment exists in the ledger, because cache eviction or failover can remove that entry.

The deployment target is Kubernetes on three availability zones. The namespace is payments-prod, and the service account is payment-orchestrator.

For service-to-service calls, we are standardizing on gRPC with protobuf. The public API remains REST under /api/v2/payments, so clients do not need to know about the internal transport.

The gRPC method is ProcessPayment, and the protobuf package is payments.v2. We should preserve the field name payment_id because downstream consumers already depend on it.

For consensus inside the configuration service, we use ETCD. The leader election timeout is 1000 milliseconds and the heartbeat interval is 100 milliseconds.

The rough algorithm is only relevant to the metadata cluster, not the payment ledger. I want that distinction in the documentation because people keep mixing the two consistency mechanisms.

Right, and the metadata cluster has five nodes. Losing two nodes is tolerated, but if we lose three, the cluster cannot maintain quorum and writes stop.

On observability, Prometheus is scraping the application metrics and Grafana is rendering the dashboards. The scrape interval is 15 seconds.

We are also adding OpenTelemetry tracing. Trace IDs must propagate through the Kafka headers so that checkout, orchestration, and the gateway can be correlated.

For the state machine, CREATED moves to AUTHORIZING, then AUTHORIZED or DECLINED. An AUTHORIZED payment can move to CAPTURED, but a DECLINED payment cannot move directly to CAPTURED.
